# Practice question bank — Supabase setup

Free Postgres backing the `/practice` question bank and submission logging.
Runs entirely through Next.js API routes (`app/api/practice/*`) calling
Supabase's REST API via `@supabase/supabase-js` — no separate server, no raw
DB connection string needed. (The earlier FastAPI/Docker prototype in
`backend/` at the repo root is unused but left in place.)

We deliberately do **not** use Supabase Auth/`@supabase/ssr` here — this is
public content with no logins, so the session/cookie/middleware plumbing
those packages provide doesn't apply.

## 1. Create a Supabase project

Free at [supabase.com](https://supabase.com) → **New project**.

## 2. Create the tables + RLS policies

Open **SQL Editor** in the dashboard, paste in [`schema.sql`](schema.sql),
run it. This also enables Row Level Security with two policies:

- `questions`: public **read**, no public write (so the anon key exposed to
  the browser can't be used to deface the question bank)
- `submissions`: public **insert** only, no read (anyone can log an attempt,
  nobody can read anyone's back through the API)

## 3. Seed the question bank

Also in the SQL Editor, paste in [`seed.sql`](seed.sql) and run it — it
upserts the 4 questions from `scripts/seed-data.mjs` by `slug`.

If you add/edit questions in `scripts/seed-data.mjs`, regenerate it:

```bash
cd portfolio/portfolio
node scripts/generate-seed-sql.mjs > db/seed.sql
```

then paste the new `db/seed.sql` into the SQL Editor again.

## 4. Env vars

Copy `.env.local.example` to `.env.local` and fill in from **Project
Settings → API**:

```
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=...
```

Both are safe to expose client-side — RLS is what actually restricts access,
not key secrecy.

## 5. Run locally / deploy

```bash
npm run dev
```

Visit `http://localhost:3000/practice` — it now reads from Supabase instead
of the bundled fixture fallback.

For Vercel: **Settings → Environment Variables** → add the same two vars,
redeploy.

## Adding a new question

Add an entry to `scripts/seed-data.mjs`, regenerate `db/seed.sql` (step 3),
paste-run it. Same field shapes as `db/schema.sql`:

- **SQL question:** `schema_sql` / `seed_sql` are **SQLite dialect** — they
  run client-side in the browser via sql.js, not against this Postgres DB.
- **Python question:** `seed_data` is `{table_name: [row_dict, ...]}`, loaded
  into pandas DataFrames client-side via Pyodide.
- `order_matters: false` lets the frontend compare rows as an unordered set.

## Fallback behavior

If the Supabase env vars are missing or the API call fails, the Next.js API
routes return 503 and `lib/practiceApi.js` transparently falls back to the
same 4 questions bundled in `lib/practiceFixtures.js` — the practice UI keeps
working, just without persisted submission logging.

## Not yet wired

`GET /api/practice/submissions/[sessionId]` (per-session submission history)
is stubbed to return 501 — `submissions` has no public SELECT policy by
design, so the anon key can log an attempt but can't read any back. Revisit
with a scoped policy (or a server-only `service_role` key) if that becomes a
real feature.

# Retail demo data (`/api/retail/*`)

Demo data for a fictional US apparel chain, **Cobalt Lane Apparel**, so the site
can show each LinkedIn video's allocation scenario running on real-looking data:
40 stores in real US cities (with real climate differences), 2 DCs, 7 vendors,
25 styles, 26 weeks of store × style sales, store and DC positions, 130 POs with
promised vs actual lead times, this week's inbound ship notices (ASNs), and the
"hero" cases from every video planted in it.

Everything is generated by one deterministic script, `lib/retail/generate.js`, so
the Supabase copy and the in-memory fallback are identical, number for number.

## Load it into Supabase

In the SQL Editor, paste and run, in order:

1. [`retail-schema.sql`](retail-schema.sql): tables + RLS (public read-only, like `questions`)
2. `retail-seed-1.sql`, then `retail-seed-2.sql`, `retail-seed-3.sql`, …

All are safe to re-run. Part 1 clears the retail tables first; the later parts
only add weekly sales. The app keeps serving its in-memory copy until the last
part has run, because that's where the `retail_meta` marker row goes.

### Upgrading from v1 (the cross-dock video)

If you seeded before the cross-dock video, you don't need to reload everything.
Paste `retail-schema.sql` again (it adds `retail_asn_lines`), then
[`retail-upgrade-v2.sql`](retail-upgrade-v2.sql). Until then, the cross-dock page
runs on the in-memory copy (its badge says "Demo data") and every other page keeps
reading Supabase. `retail_meta.data_version` says which version is loaded.

If you change the generator, rebuild the seed files and paste them again:

```bash
npm run retail:seed
```

## Without Supabase

If the retail tables aren't there (or the env vars aren't set), the API routes
generate the same dataset in memory and serve that. The responses say which one
they used: `"source": "supabase" | "generated"`. Set `RETAIL_SOURCE=generated` to
force the in-memory copy.

## Use cases

`GET /api/retail` lists them; `GET /api/retail/<id>` runs one. Query params
override the defaults, e.g. `/api/retail/size-curves?style=CREW-TEE&store=41`.

| id | video | what it decides |
|---|---|---|
| `agentic-overview` | Agentic AI in retail | stockouts before the next truck, transfers, excess, replenishment levels |
| `avg-per-store` | Average per store | forecast vs average-per-store, per item |
| `size-curves` | Size curves | chain vs own vs cluster curve per store; broken sizes |
| `fixed-push` | Fixed push | push plan, censored "zero demand", reserve release |
| `store-depth` | Store depth | gap-fill vs push, stale depth targets, method flags |
| `end-of-season` | End of season | flush / hold / off-price per item, recovery math |
| `bullwhip` | Bullwhip effect | shopper demand vs store orders vs DC orders; PO check |
| `lead-time` | Lead-time variability | vendor reliability, drift, safety stock per vendor |
| `cross-dock` | Cross-dock at receipt | per ASN line and store: straight to store doors or into reserve; dock-to-store days, touches, sales protected |

The engines (`lib/retail/engine/*`) are deterministic rules over the data, with no
model calls. `npm run retail:check` runs all of them and checks each video's story
still shows up in the numbers.
